# 構文拡張ロードマップ（2026-07-19）

今後ありえる構文追加の候補を、実装するかはさておき ROI 順に整理したもの。
ここでの ROI = 価値（ユーザーに見える効果・既存ドキュメントとの整合）÷
コスト（AI 開発の時間・token を含む実装/テスト/保守の総量）。

## 前提: この設計の非対称性

現在のアーキテクチャ（文字列正規化 → AST プラグイン → カスタム要素 →
`ink-*` クラスのデフォルトレンダラ）では、追加コストが層によって大きく違う:

- **安い層**: コードフェンスの種類追加、`@[...]` embed の種類追加、
  インライン記法の追加（既存のパターンに1ケース足すだけ）
- **高い層**: 外部スクリプトを要する埋め込み（X/Twitter 等）、
  トランスクルージョン（再帰・循環検出・アプリ側 API が絡む）

また manifest 自身が「追加は安全、改名・削除は破壊的」と宣言しているので、
増やす方向に設計上の無理はない。

## 採用判断の基準（2つで足りる）

1. **シードする構文ガイドに載せる価値があるか** — ガイド自体を
   コンテンツとして配っている以上、「ガイドに書いてあるのに動かない」は
   それだけで対応理由になる（wikilink・link-card で実証済みのパターン）
2. **アプリ知識が要る部分を注入パターンに逃がせるか** —
   `resolveWikilink` / `ogpEndpoint` と同型の「解析はライブラリ、
   解決はアプリ」の分担が組めるなら受け入れてよい

## 候補一覧（ROI 順）

### P1: `==ハイライト==` → `<mark>`

- **根拠**: v1 に `remark-mark` の実装が既にあり、シード済みガイド
  `extended.md` が「プラグインがあれば `<mark>` になる」と文書化済み。
  現状は「ガイドに書いてあるのに動かない」状態。
- **コスト**: 極小。v1 の移植（micromark-extension-mark +
  mdast-util-mark 依存の追加）。テストは既存パターンの複製。
- **ROI**: 最高。ガイドとの不整合解消という明確な価値に対し、
  実装は事実上コピー。

### P2: コードフェンス行ハイライト `{1,3-5}` / `showLineNumbers`

- **根拠**: `remarkCodeMeta` が metastring を既に配管済みで、
  `parseCodeMeta` の拡張だけで済む。技術記事系 KB では定番機能。
- **コスト**: 小。新規プラグイン不要、`code-block.tsx` 内で完結。
- **ROI**: 高。配管済みの上に乗るだけ。

### P3: KaTeX 数式 `$...$` / `$$...$$`

- **根拠**: Zenn 互換の残りで最大の欠け。KB 用途で需要が高い。
- **コスト**: 中。`remark-math` + katex を optional peer dependency +
  遅延チャンクにする — mermaid で確立済みのパターンをなぞるだけで
  設計的な新規性はゼロ。CSS（katex.css）の消費者側ロードの案内が要る。
- **ROI**: 高。パターン確立済み × 需要大。

### P4: `[[note#見出し]]`（アンカー付き wikilink）

- **根拠**: wikilink をタイトル解決で実装した時点での自然な「次」。
  スラッグ機構（`slugify` / heading id）が両側に既にある。
- **コスト**: 小〜中。`remark-wikilinks` のパースで `#fragment` を
  分離し resolver に渡す or URL に素通しするだけ。
  ※着手前に 見出しスラッグの wikilink ズレ（修正済み、`d3b3ce3`）を
  先に直すこと — 同じ領域のバグの上に機能を積まない。
- **ROI**: 中〜高。KB としての内部リンク精度が一段上がる。

### P5: `@[...]` embed の種類拡充

- **根拠**: shorthand は現在 `card` / `github` の2種のみ。zenn-editor
  本家は `@[youtube](ID)` `@[gist]` `@[codepen]` `@[speakerdeck]`
  `@[figma]` など10種以上。
- **コスト**: 種類による。
  - `@[youtube](ID)`: 極小（URL 形への正規化だけ、レンダラは既存）
  - iframe 系（codepen/speakerdeck/figma 等）: 小〜中（レンダラ追加）
  - `@[tweet]`: 高（外部スクリプト注入が必要）。X 埋め込みは
    mermaid 型の optional peer + lazy chunk にするか、
    リンクカードへのフォールバックで妥協するかの判断が要る
- **ROI**: `@[youtube]` だけ先行して P5 とし、残りは需要が出てから。

### P6: chart:line / chart:pie

- **根拠**: フェンス種追加は最安層。recharts が両方サポート済み。
- **コスト**: 小。`parse-chart-fence` の type 拡張 + レンダラ分岐。
- **ROI**: 中。コストは安いが、実際に使う文書があるかが未知数。
  需要（書きたい文書）が現れてからで十分。

### P7: `![[note]]`（トランスクルージョン / 文書埋め込み）

- **根拠**: wikilink の `!` 前置形。Obsidian 系 KB の定番機能で、
  方向性としては本命。
- **コスト**: 高（候補中最大）。構文解析はライブラリ側で安いが、
  本文取得のアプリ側 API（embed エンドポイント注入 —
  `ogpEndpoint` と同型）、再帰埋め込みの深さ制限、循環検出、
  部分レンダリング（見出しだけ埋める `![[note#sec]]`）まで
  考えると設計・テストの総量が大きい。
- **ROI**: 中。価値は大きいが分母も大きい。P4（アンカー付き
  wikilink）を先に済ませ、resolver 契約の拡張として設計すると
  手戻りが減る。

### P8: `~sub~` / `^sup^`

- **根拠**: ガイド `extended.md` が「非標準、プラグイン必要」と言及。
- **コスト**: 小（remark-sub/sup 系の導入 or 自前インライン記法）。
- **ROI**: 低〜中。P1 と違い v1 にも実装がなく、ガイドも
  「対応していない」前提の書き方なので不整合ではない。
  日本語 KB で上付き/下付きの実需要が出てから。

## 先にやるべき「既存表面の穴埋め」（新構文より優先）

- **`columns` レンダラの欠落**: manifest に `Columns` が登録され
  ペアリングもされるのに `inkstreamDefaultComponents` にレンダラがない
  （`cardgroup` はあるのに）。未知のカスタム要素として出力され
  実害は小さいが、新構文を足す前に塞ぐべき既存の穴。
- 既知バグ群（wikilink 見出しスラッグ含め修正済み。WORKPLAN 参照）。
  P4/P7 は §1-1 修正が前提。

## 見送り（当面やらない）

- **`#tag` インライン記法**: 検索・索引などアプリ側機能とほぼ一体で、
  レンダリングだけ先行しても価値が薄い。
- **`[toc]` ディレクティブ**: kb_practice は TOC を `.ink-markdown` の
  外側（`extractMarkdownHeadings` + 自前コンポーネント）で描画する
  分担を確立済みで、文書内 TOC は分担境界を壊す。
- **Mintlify の残りタグ（Frame / Icon / Expandable 等）**:
  実文書に現れたら追加する。manifest 追加は安全なので
  先回りする必要がない。

## まとめ

推奨着手順: **P1 → P2 → P3** までは「確度が高く安い」ので一括で
やる価値がある。**P4** は wikilink 見出しスラッグ修正（済）が前提だった。
**P5 以降は需要駆動**（実際に書きたい文書が現れてから）に切り替え、
先回り実装はしない。
